# 代码任务执行服务设计

本文是实现前的设计。下面的接口、默认值和验收场景是后续实现的约定，测试结果在实现后记录。

## 1. 目标与运行条件

评审在本机启动服务，提交一个预置 Python 项目的检查、测试或构建任务，立即取得任务 ID。服务为每次提交复制一份项目，同时最多执行两个任务。调用方能在执行期间读取日志或取消任务，结束后能查询退出原因、执行报告和构建产物。

第一版面向 Linux 和 macOS 上的单用户本地演示。服务默认监听 `127.0.0.1`，以当前普通用户身份运行。项目由维护者随仓库提供，调用方只能选择项目 ID 与任务类型。项目中的测试代码拥有执行用户的文件和网络权限；独立目录解决的是不同任务写入同一份源码的问题。接收外部用户上传的代码需要另一层执行隔离。

## 2. 一次任务如何执行

采用 Python 3.11+、FastAPI、单进程 Uvicorn 和 SQLite。HTTP 请求与子进程 I/O 共用一个 asyncio 事件循环，任务代码在独立的操作系统进程中运行。SQLite 同时保存队列和历史，便于重启后按原 ID 查询，也省去数据库与另一套消息队列对账的工作。

| 职责 | 实现约定 |
| --- | --- |
| HTTP 层 | 校验输入，提交、读取或取消任务，返回稳定的响应。创建请求在任务入库后即可返回 |
| 调度与存储 | SQLite 保存任务 ID、入队序号、请求参数、状态、时间、退出信息、截断标记和产物。两个常驻 worker 按入队序号领取任务。领取与状态修改在同一短事务中完成 |
| 执行器 | 根据只读项目表定位源目录，在数据目录的 `work/<id>/` 下创建私有副本。启动固定命令、读取日志、处理停止请求、发布产物并清理目录 |

项目本身保持小且可审查。成功示例含可执行的 `__main__.py` 和通过的测试，失败示例含一条会失败的断言。任务类型的映射如下。解释器取服务自己的绝对路径，命令以参数数组传入，工作目录设为项目副本。

| 类型 | 对预置项目执行的操作 | 验收结果 |
| --- | --- | --- |
| `lint` | 用 `python -m compileall -q .` 做 Python 语法检查 | 语法错误产生非零退出码，检查范围在 README 中注明 |
| `test` | 用 `python -u -m unittest discover -s tests -v` 执行项目自带测试 | 可从日志读到用例名和失败原因，执行报告记录实际退出码 |
| `build` | 用 `python -m zipapp . -o <输出目录>/app.pyz` 生成归档 | 输出目录位于源码副本外；E2E 下载归档后用 Python 运行它，核对示例输出 |

这里的 unittest 是被测示例项目的任务负载。服务自身用跨 HTTP、数据库重启和真实子进程的 E2E 验收。

## 3. HTTP 契约

创建一个任务的示例请求体为 `{"project_id":"hello","type":"test","timeout_seconds":30}`。成功响应为 HTTP 202，并返回 `{"id":"<uuid>","status":"queued"}`。这个状态代表入队时刻，首次查询时任务可能已经完成。每次成功提交都创建独立任务。

| 接口 | 成功响应与边界行为 |
| --- | --- |
| `POST /tasks` | 必填字段为 `project_id` 和 `type`。超时可省略，默认 30 秒，接受 1–300 的整数。未知项目、类型、额外字段或非法超时返回 422。等待队列满返回 429 |
| `GET /tasks/{id}` | 200，返回 ID、项目、类型、超时、状态、`created_at`、`started_at`、`finished_at`、`exit_code` 和 `error`。时间为 UTC RFC 3339。尚未发生的时间和未取得的退出码为 null。错误用稳定的 code 和简短 message 表示 |
| `GET /tasks/{id}/logs` | 200，返回 `{"text":"…","truncated":false}`。合并 stdout、stderr，返回截至查询时已收集的输出。尚无输出时返回空字符串。支持轮询 |
| `POST /tasks/{id}/cancel` | 队列中取消返回 200 和终态快照。运行中登记停止请求，返回 202 和当前快照，客户端继续查状态。再次取消返回当时快照；已结束时返回 200 和原终态 |
| `GET /tasks/{id}/artifacts` | 200，响应为 `{"items":[]}` 或含 `name`、`size_bytes`、`download_url` 的列表。终态发布前列表为空。成功构建包含可下载的 `app.pyz` |
| `GET /tasks/{id}/artifacts/{name}` | 200，返回已发布产物的原始字节。按任务 ID 与产物名查库，未知产物返回 404 |

各任务查询及取消接口对不存在的 ID 均返回 404。非零退出码属于任务结果，查询这个结果本身仍返回 200。测试失败的典型结果为 `status=failed`、`exit_code=1`、`error.code=nonzero_exit`，具体断言见日志。

## 4. 状态、取消与超时

| 当前状态 | 事件 | 新状态与处理 |
| --- | --- | --- |
| queued | worker 领取 | running；填入开始时间，启动执行期限 |
| queued | 取消 | cancelled；只填结束时间，退出码为空，不创建工作目录 |
| running | 正常退出 | 退出码 0 且产物收集与清理成功则 succeeded；非零则 failed |
| running | 启动、产物收集或清理失败 | failed；记录失败阶段和实际取得的退出码 |
| running | 收到取消或达到执行期限 | 停止进程组、回收直接子进程并清理。成功后按原因记录 cancelled 或 timeout |
| 任一终态 | 再次取消或迟到的完成通知 | 保留已发布结果和结束时间 |

每个运行任务由一个 worker 负责写终态。worker 在第一次等待 I/O 前注册任务控制记录，取消接口和计时器通过它登记原因。事件循环**先登记的完成、取消或超时事件生效**；检查和登记之间不让出事件循环。清理期间仍可查日志，状态暂为 running。若已登记自然完成，此时的取消只返回快照。若清理本身失败，最终标记 failed，保留原停止原因供诊断。退出码采用子进程实际返回值；POSIX 信号终止保留负信号编号。

超时使用单调时钟，从领取任务起算；排队耗时可由创建与开始时间相减得到。复制和收集只处理大小受控的预置样例。创建进程前再检查停止原因，若停止请求恰好发生在启动期间，取得进程句柄后立即执行回收。终态时间包含必要的清理，可能晚于超时点。

## 5. 资源边界与收尾顺序

- **并发与输入。** 默认两个 worker，最多另有 32 个 queued 任务，入队上限检查与插入同一事务完成。请求里的字符串只能匹配预置项目表和任务表。子进程通过 `create_subprocess_exec` 启动，使用固定参数、最小环境和空 stdin。预置源码不包含符号链接。
- **进程。** POSIX 下为每个任务创建独立会话。取消、超时或主进程退出后，都检查并终止该任务组内的剩余进程。先发 TERM，给短暂宽限（默认 1 秒），必要时发 KILL，同时持续读取输出。直接子进程由执行器 wait 回收。后代若主动创建新会话，可脱离该控制范围。
- **日志。** 从合并管道按块读取，保存前 64 KiB 原始字节到任务私有日志文件，使轮询能及时读取。首次溢出设置持久化截断标记，其后继续排空管道并丢弃超额数据，避免任务被写满的管道阻塞。响应以 UTF-8 解码，不完整或非法序列用替换字符展示。父进程退出和日志 EOF 分开观察，避免仍持有管道的后代拖住回收。
- **产物。** 服务生成小型 `result.json`，记录任务 ID、类型、终态、退出码与错误。正常收尾的运行任务都有报告，包括测试失败的任务。成功构建额外收集固定文件 `app.pyz`，只接受普通文件，上限 5 MiB。大小或文件类型异常则构建失败。队列中取消和崩溃中断允许产物为空。
- **发布顺序。** 停止并回收进程 → 排空日志 → 读取允许的产物到有界内存 → 删除工作目录 → 在同一 SQLite 事务写入产物和终态。产物用 BLOB 保存，读取与下载不依赖原目录。清理失败记录 `cleanup_failed`，保留残留目录供启动时重试，不发布成功构建。服务只清理专用 work 根目录下自己创建的任务目录。

## 6. 停机、重启与已知限制

数据目录只允许一个服务实例持有，通过进程级独占文件锁避免第二个实例误清理正在运行的任务。正常停机时停止接单和领取任务，保留 queued 记录，对运行中任务请求停止、收尾并记录 `cancelled` 与 `service_shutdown` 原因，最后释放锁。

重启取得锁后、对外提供服务前，清理遗留工作目录，将数据库里遗留的 running 记录转为 failed，记录 `service_interrupted` 和恢复时刻，退出码留空。若目录清理失败，启动报错并给出目录，供维护者处理后重试。queued 按原顺序继续执行；已完成任务的状态、已落盘日志和已发布产物可查。中断任务不会自动重跑，避免同一提交被执行两次。

服务自身遭遇 SIGKILL 时无法执行收尾。重启能恢复记录、清理目录，**仅凭 SQLite 里的记录无法证明上次启动的进程组已消失**。恢复时也不按旧 PID 发信号，以免 PID 复用后误伤其他进程。该版本的进程回收保证覆盖服务正常运行和优雅停机；强杀的系统级回收留作明确限制。另外，日志和产物的上限按任务计算，长期运行需要历史保留策略。

## 7. E2E 验收与演示

计划入口为 `python -m pytest -q tests/e2e`。测试夹具在临时数据目录启动真实服务，通过 localhost HTTP 发请求。慢任务先打印就绪标记再等待，由测试观察标记后发起取消或检查并发。轮询均设截止时间，失败时保留最后一次状态与日志。下表是待实现和运行的验收清单。

| 场景 | 通过条件 |
| --- | --- |
| 成功、失败、构建 | 对三个任务分别断言状态和退出码；失败日志包含预设断言；下载执行报告并核对 ID；下载构建归档并实际运行成功 |
| 并发与排队 | 两个慢任务各自输出就绪标记且同时 running；第三个保持 queued，释放一个槽后才启动。相同项目同时写入各自副本时互不覆盖 |
| 队列中取消与重复取消 | 取消等待者后一直是 cancelled，开始时间为空；再次取消不改结束时间；释放槽后该任务仍未执行 |
| 运行中取消与超时 | 分别停止一个带子进程的任务；断言终态、工作目录消失、已知子进程停止活动。随后一个短任务成功，证明执行槽可复用 |
| 取消与自然结束交错 | 在可控结束点前后分别发起取消，检查首个已登记事件对应的终态；反复查询和取消，结束时间、退出码及产物列表一致 |
| 日志限量 | 任务分别写 stdout 和 stderr，等待时已可读；再输出超过 64 KiB，断言截断标记、ASCII 样例字节上限及任务能正常退出 |
| 非法请求与容量 | 检查额外命令字段、未知项目和类型、非法超时返回 422；不存在任务或产物返回 404；填满等待队列后再提交返回 429 |
| 重启 | 优雅停机后验证运行任务已取消、排队任务恢复；受控强杀后验证遗留 running 变为 failed、终态任务的产物可下载。强杀夹具自行回收它创建的测试进程 |

演示脚本复用同一套预置项目，从启动服务开始，依次展示成功、失败、取消运行中的任务，再展示运行中读到的日志和清理后下载的产物。最后打开一条实际跑过的 E2E，对照 `AI_USAGE.md` 解释 AI 参与、人工判断和验证结果。实现完成后，README 将给出在干净环境中启动、跑测试和重放演示的命令。

## 8. 如果再给一天

优先在 Linux 上把每个任务交给独立的受监管执行单元，例如绑定服务生命周期的 systemd 单元并按 cgroup 回收。验收时强杀服务，让测试从操作系统侧检查任务后代确实退出，再启动服务核对任务记录。这样可以补上当前设计最难用应用层状态推断的缺口，也能给后续的内存与进程数配额提供基础。
