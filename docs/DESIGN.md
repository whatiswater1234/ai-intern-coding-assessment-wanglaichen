# macOS 本机代码任务执行服务

评审在 Mac 上启动服务，提交一个预置项目，拿到任务 ID 后就可以查进度、读日志或取消执行。服务用当前用户的权限，在每个任务自己的目录中运行语法检查、测试或构建。构建成功后，即使临时目录已经删除，评审仍能下载并运行产物。

本文约定后续实现及验收方式。开发、运行、故障演练和演示均在同一台 Mac 上完成。

## 1. 本机环境与启动方式

已检查开发机为 Apple Silicon，macOS 26.6.2，系统解释器 `/usr/bin/python3` 为 3.9.6，可使用 SQLite 3.51.0、kqueue 和 flock。设计使用这套解释器的标准库：`http.server` 提供本地 HTTP 接口，`sqlite3` 保存任务，`subprocess`、`select` 和 `signal` 管理系统进程。命令数和路由数固定，使用标准库可以让评审在仓库根目录直接启动服务。

| 实现后提供的入口 | 作用 |
| --- | --- |
| `python3 -m task_service` | 前台启动，默认监听 `127.0.0.1:8765`。数据保存在仓库的 `.task-service/`，由启动程序创建，加入 Git 忽略列表 |
| `python3 -m unittest discover -s tests/e2e -p 'test_*.py'` | 启动真实服务，使用独立临时数据目录和本机临时端口，走 HTTP 验收 |
| `python3 scripts/demo.py` | 使用独立数据目录启动服务，演示成功、失败、取消、看日志和下载归档，结束时关闭自己的服务 |

任务代码来自仓库内由维护者提供的项目。开发者用普通账号运行服务，同一目录中的两个服务实例由文件锁互斥。隔离目录能防止两个正常任务写坏同一份源码；任务仍能访问当前账号有权访问的文件和网络。这一信任边界决定了接口只接受预置项目 ID，并要求项目的后代进程留在本任务进程组内。

## 2. 从一次构建看各部分职责

1. HTTP 接口收到 `POST /tasks`，校验 `{"project_id":"hello","type":"build"}`。任务写入 SQLite 后才返回 202 和 ID。因此，客户端收到成功响应时，任务已经入队。
2. 调度器按入队序号领取任务。默认最多两个 running、另有 32 个 queued。每领取一个任务，启动一个独立的 Python 执行器进程（下文称 runner）。HTTP 请求无需等待任务完成。
3. runner 在 `work/<id>/` 创建私有目录，将源码复制到 `src/`，在该目录运行固定命令。以构建为例，输出路径是同级的 `out/app.pyz`，归档不会包含自身。runner 持续收集输出，同时处理截止时间和取消。
4. 命令结束后，runner 回收进程组，检查产物，暂存结果，删除本次工作目录，然后发布终态。评审此时能通过 HTTP 下载归档，用本机 Python 执行。

| 任务类型 | 执行内容 | 结果判定 |
| --- | --- | --- |
| lint | `python -m compileall -q .` | 检查 Python 语法，退出码为 0 即通过 |
| test | `python -u -m unittest discover -s tests -v` | 执行示例项目自带测试。失败时保留断言、stderr 和非零退出码 |
| build | `python -m zipapp . -o <输出目录>/app.pyz` | 命令成功且归档校验通过，方可标记 succeeded |

实际启动均使用当前解释器的绝对路径和参数数组。只有维护者能定义项目目录、命令和产物名。项目或任务类型不在表内时，校验阶段直接返回错误。

独立 runner 的作用是让任务期限、进程句柄和收尾逻辑有同一个所有者。API 意外退出时，活着的 runner 仍能按时结束命令、写回结果。两个执行槽最多对应两个活动 runner。

## 3. HTTP 接口

创建请求只接受 `project_id`、`type` 和可选的 `timeout_seconds`。超时默认 30 秒，接受 1–300 的整数；拒绝布尔值、额外字段、任意命令和用户提供的路径。超时从领取时开始，排队时长由 started_at 与 created_at 的差值得出。

| 接口 | 调用方看到的结果 |
| --- | --- |
| `POST /tasks` | 202，返回 `{"id":"<uuid>","status":"queued"}`，Location 指向状态接口。再次提交会创建新任务 |
| `GET /tasks/{id}` | 200，返回下方的任务快照。所有时间为 UTC RFC 3339，尚未发生的事件为 null |
| `GET /tasks/{id}/logs` | 200，返回 `{"text":"…","truncated":false}`。允许在执行中轮询，尚无输出时 text 为空 |
| `POST /tasks/{id}/cancel` | 排队中直接取消并返回 200；运行中登记停止请求并返回 202；任务已结束时返回 200 和原快照 |
| `GET /tasks/{id}/artifacts` | 200，返回 `{"items":[]}` 或含 name、size_bytes、download_url 的列表。终态发布前列表为空 |
| `GET /tasks/{id}/artifacts/{name}` | 200，以记录的媒体类型返回原始字节；按任务 ID 和完整产物名查库 |

失败测试的状态快照：

```json
{
  "id": "bd28a470-f4f7-4717-9c47-4dabefd9771a",
  "project_id": "broken", "type": "test", "timeout_seconds": 30,
  "status": "failed", "exit_code": 1,
  "created_at": "2026-01-01T10:00:00Z",
  "started_at": "2026-01-01T10:00:01Z",
  "finished_at": "2026-01-01T10:00:02Z",
  "stop_reason": null, "recovery_reason": null,
  "error": {"code":"nonzero_exit","message":"项目测试退出，退出码为 1"}
}
```

请求错误统一返回 `{"error":{"code":"…","message":"…"}}`。无效 JSON 为 400，请求体超过 8 KiB 为 413，创建请求媒体类型有误为 415，字段校验失败为 422，未知任务或产物为 404，等待队列满为 429，存储暂不可写为 503。非零退出码是任务结果，查询这个结果仍返回 200。

## 4. 状态与持久化

SQLite 与临时目录放在本机文件系统。HTTP 线程、调度器和 runner 分别使用自己的连接，开启 WAL、外键和有界 busy timeout。写事务只包含数据库操作，复制文件、等待命令和清理目录都在事务外执行。

| 数据 | 保留内容 |
| --- | --- |
| tasks | 唯一任务 ID、递增入队序号、请求参数、状态与时间、截止时间、首次登记的结束原因、退出码、错误及收尾进度 |
| task_logs | 每任务的原始字节前缀与截断标志 |
| artifacts | 由任务 ID 与产物名唯一标识，保存媒体类型、大小和内容 |
| 工作目录与锁 | `work/<id>/{src,out,tmp}` 只保存执行期文件。API 实例锁与每个 runner 的锁放在 work 之外，工作目录清理后仍可核对所有权 |

**允许的流转。** queued 可进入 running 或 cancelled；running 可进入 succeeded、failed、timeout 或 cancelled。创建时记录 created_at，领取时记录 started_at，终态发布时记录 finished_at。排队取消保留空的 started_at 和 exit_code。命令受信号终止时保留实际负信号编号，未启动或退出码无法取得时为 null。

**竞态规则。** 容量检查和入队共用一个写事务。领取使用带 queued 条件的更新，排队取消亦然。运行中取消、超时和自然退出通过条件更新登记首个结束原因，重复调用读取已有决定。若已过截止点且还没有决定，登记 timeout。命令可能已经物理退出、runner 尚未登记完成，这时先登记成功的取消请求可以生效。终态一旦发布，其结束时间、错误和产物均保持一致。

**结果发布。** runner 为正常收尾的已领取任务生成 result.json，成功构建另有 app.pyz；排队取消没有产物。先用一个事务暂存报告、文件和候选结果，确认工作目录已删后再发布终态。下载只查询已发布记录。目录删除失败时保留执行槽与暂存结果，设置 recovery_reason 并退避重试。默认保留终态记录七天，过期时通过外键一并删除日志和产物。活动任务及待清理记录继续保留。

## 5. Mac 上的进程、目录与日志

**路径和权限。** 工作目录权限为 0700。源码复制只接受目录与普通文件，拒绝符号链接和特殊文件。子进程使用固定 cwd、空 stdin、最小环境和任务私有 HOME、TMPDIR。仅收集约定文件名，基于服务持有的输出目录描述符打开，使用 O_NOFOLLOW 和 fstat 校验普通文件，按实际读取字节限制归档为 5 MiB。任务进程关闭无关文件描述符。

**进程组回收。** runner 和任务命令各自建立会话。runner 用 `Popen(..., start_new_session=True)` 启动命令，在组外监管它。通过 macOS 的 kqueue NOTE_EXIT 观察组长退出，暂缓 wait，以保留组长 PID 的身份。超时、取消或主命令自然退出都要处理组内后代：先发 SIGTERM，给短暂宽限，再发 SIGKILL 结束剩余成员，最后 wait 取得直属子进程退出码。这样，即使测试主程序成功返回却留下一个占着输出管道的后台进程，服务也能完成回收。API 正常运行时同步回收自己启动且已退出的 runner。

**输出与期限。** stdout 和 stderr 合并到非阻塞管道；读固定大小的块，每轮给取消和单调时钟检查留出机会。保留前 65,536 个原始字节，读到第 65,537 个字节才设置 truncated。达到上限后继续排空管道，避免写满后卡住命令。每隔最多 250 ms 发布新前缀，结束时再刷新，响应以 UTF-8 替换无效字节。日志 EOF 和命令退出分别观察。命令开始前也检查取消和期限，复制源码的时间计入任务超时。

## 6. 关闭与重启

调度器领取前持有该任务的独占 flock，通过 pass_fds 将锁交给 runner；父进程在交接后关闭自己的描述符，任务命令不继承锁。同一数据目录只能启动一个 API。重启后先查 running 记录及对应锁，再根据已有运行数分配执行槽。

| 重启时看到的情形 | 处理 |
| --- | --- |
| 任务还在排队 | 以原 ID、原顺序继续调度 |
| 已领取，锁已释放且命令尚未启动 | 清理准备目录，以 failed / service_interrupted 收尾，不重复执行 |
| 原 runner 持锁 | 继续使用原 runner。新 API 可读日志并接受取消，旧任务仍计入两个执行槽 |
| 结果已暂存，原 runner 已退出 | 补做目录清理，发布原结果。目录已不存在即视作清理完成 |
| 任务已进入终态 | 直接读取先前的快照和产物 |

正常按 Ctrl-C 时停止接单和领取，登记运行项的 service_shutdown 原因，由 runner 取消并收尾，等待项留给下次启动。强杀 API 时 runner 可以继续执行；这两类场景分别验收。

若 runner 自身被强杀，启动命令前持久化的标志用于识别“可能仍有活进程”。锁已释放且标志仍在时，保留工作目录和执行槽，对外给出 running 与 `recovery_reason=cleanup_unverified`。维护者确认进程已消失后，方可清理并以 failed / runner_lost 收尾。恢复程序不会根据历史 PID 向当前 Mac 上的其他进程发信号。存储写入失败时优先停止在途子进程，确认写入后才向调用方报告结果。

## 7. 本机 E2E 和演示

自动化测试启动真实服务，通过 HTTP 提交任务，并从 macOS 一侧检查进程、文件和下载结果。慢任务打印就绪标记；测试看到标记才触发取消或强杀，轮询设置截止时间。检查进程消失与目录清理后，测试夹具才执行兜底清理。

| 场景 | 通过条件 |
| --- | --- |
| 成功、失败和构建 | 真实命令给出对应退出码。失败日志含预期断言。工作目录删除后仍可下载 app.pyz 并运行，输出与示例一致 |
| 并发、隔离和排队 | 两个慢任务同时就绪，写同名文件时各自读回自己的内容；第三个等待。等待队列满返回 429，空出槽后按序领取 |
| 取消和超时 | 排队取消没有开始时间或工作目录。运行取消、超时均回收忽略 TERM 的同组后代，下一任务取得槽。重复取消保持原结束时间 |
| 主命令提前结束 | 主命令退出码为 0，仍持有管道的同组后代消失，日志查询与结果发布可以完成 |
| 日志边界 | 运行中能读两种输出流，恰好上限与超一字节的截断标志不同。持续输出、无换行、多字节截断均能收尾 |
| 非法请求与文件 | 断言输入错误和未知 ID 的响应，检查链接型与超大产物被拒绝，原始预置项目内容保持一致 |
| 停机、重启和锁 | Ctrl-C 后运行项被取消；强杀 API 后 runner 按期结束；在 runner 活跃时重启可用原 ID 取消，排队任务与既有产物仍可查。第二实例不能占用同一数据目录 |
| 收尾中断 | 分别在暂存后、删除后中断 runner，恢复为同一份结果。失去监管时能观察到待核实原因 |

**已在这台 Mac 验证的机制。** 真实进程实验覆盖主动取消、上层进程被强杀后 runner 自行超时、主命令正常退出留下后台进程。三次均观察到同组中忽略 TERM 的后代消失，主命令退出码分别为 -15、-15、0。另已验证 flock 经 pass_fds 交接后，父进程关闭描述符不会释放子进程持有的锁；子进程退出后可重新取得锁。完整 HTTP 服务和上表 E2E 属于实现阶段。

演示脚本依次启动服务、提交成功和失败任务、取消一个能读到实时日志的慢任务、下载并执行归档。最后对照 AI_USAGE.md 展示一项实际采用或修改的 AI 建议及其验证记录。后续优先加固 runner 意外退出后的本机诊断与恢复，这决定了故障后何时能安全释放执行槽。
