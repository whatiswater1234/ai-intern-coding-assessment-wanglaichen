# 代码任务执行服务设计

**设计状态**：实现前的接口与验收约定。服务面向本机单用户；调用方选择仓库自带的项目，提交检查、测试或构建任务。本文中的命令、响应和测试用例说明实现应达到的行为。实际运行结果由实现后的 E2E 和演示记录给出。

## 1. 设计决策

保留 Python、FastAPI、SQLite 和两个执行槽。每个任务使用一个短生命周期的 Linux 容器，宿主支持 Linux Docker Engine 或 macOS Docker Desktop 的 Linux 容器模式。作此选择有一个具体原因：API 进程遭遇 SIGKILL 后，另一进程必须能认出旧任务、读取输出、终止其所有后代、释放临时文件。容器有稳定身份，任务代码即使派生新会话也留在同一 PID 命名空间里。代价是首次演示需要启动 Docker 并构建执行镜像。

| 部分 | 职责 | 可以据此验证的约定 |
| --- | --- | --- |
| HTTP API | 校验、入队、查询、取消、下载 | 创建响应一旦成功，保留期内重启后仍能用原 ID 查询 |
| 调度器 + SQLite | 排队、领取、记录停止原因、保存结果、发布终态 | 每个 ID 至多启动一次；任务失败后可用新 ID 手动再提交 |
| 容器执行器 | 从固定镜像和命令表创建容器，观察退出、收集文件、回收容器 | 任务进入终态时，其执行容器和私有可写层已删除 |
| 镜像内的小型入口程序 | 运行固定命令，记录子进程实际退出码，限量采集输出，独立执行超时 | API 掉线期间仍有执行时限；读取运行中输出不依赖请求一直保持连接 |

单个 API 实例、单个 SQLite 文件、同一个 Docker daemon 足以完成题目。服务默认监听 `127.0.0.1`，由控制面独占数据目录。任务镜像内含预置源码、Python 和入口程序。启动时解析本地镜像的不可变 image ID，在任务入队时记住这个 ID。运行期间没有拉取镜像、克隆仓库或安装依赖的步骤。启动前检查 SQLite 可写、独占锁、daemon 身份和镜像可用；失败时明确说明缺失条件。

## 2. 一条完整的执行路径

以 `{"project_id":"hello","type":"build"}` 为例：

1. API 验证项目与类型，生成 UUID，在短事务中检查容量并插入 queued 记录。提交后返回 202。
2. 空闲 worker 在事务中按入队序号领取，写入 running、开始时间和截止时间。每个任务的容器名由持久化的服务实例标识和任务 ID 决定。先 create，拿到容器 ID 并登记，再按该 ID start。
3. 镜像中每个项目位于固定目录。相同镜像产生相互独立的可写层，两个任务可在各自项目目录生成文件。入口程序在项目目录执行 `python -m zipapp . -o /out/app.pyz`，同时在独立的元数据目录记录有界日志与命令结果。
4. worker 取得退出结果，按固定清单读取产物，在一次事务中暂存结果和文件。暂存阶段读取状态仍是 running，外部还看不到半套产物。
5. worker 删除容器并确认已不存在，然后提交终态。此时 `GET /artifacts` 能下载 SQLite 中的归档，评审可以用 Python 运行它。日志、结果和归档的可见性不依赖已经删除的容器。

维护者在同一张任务定义表中声明工作目录、参数数组、所需产物和 MIME 类型。API 和执行器引用同一份定义，测试夹具通过专用镜像提供。

| 类型 | 固定程序及参数 | 成功标准 |
| --- | --- | --- |
| `lint` | `python -m compileall -q .` | 预置项目通过 Python 语法检查，退出码为 0。README 说明检查范围 |
| `test` | `python -u -m unittest discover -s tests -v` | 项目测试通过。预置的失败项目应返回非零，stderr 含真实断言差异 |
| `build` | `python -m zipapp . -o /out/app.pyz` | 命令成功且归档存在、类型与大小合法。E2E 下载并运行归档，核对已知输出 |

## 3. 调用方契约

请求和普通响应使用 JSON，产物下载返回原始字节。创建请求示例为 `{"project_id":"hello","type":"test","timeout_seconds":30}`。超时可省略，默认 30 秒，取值为 1–300 的整数。项目 ID、任务类型必须命中固定表。拒绝额外字段、布尔型超时、任意命令、路径和 URL。

| 方法及路径 | 成功行为 |
| --- | --- |
| `POST /tasks` | 202，返回 `{"id":"<uuid>","status":"queued"}`，Location 指向查询地址。相同请求再次提交会创建新任务；客户端在响应丢失时自动重试可能产生两次独立执行 |
| `GET /tasks/{id}` | 200，返回任务快照。started_at 指领取时刻，finished_at 指终态发布时刻。时间统一为 UTC RFC 3339，尚未发生的事件为 null |
| `GET /tasks/{id}/logs` | 200，返回 `{"text":"…","truncated":false}`。任务尚无输出时为空。stdout 和 stderr 按合并管道的到达顺序展示；允许轮询 |
| `POST /tasks/{id}/cancel` | 排队中直接返回 200 和 cancelled 快照。运行中持久化取消请求后返回 202 和当前快照；若先前已接受其他结束原因，202 返回当前处理状态。任一终态上调用均返回 200 和原快照 |
| `GET /tasks/{id}/artifacts` | 200，返回 `{"items":[]}` 或每项含 name、size_bytes、download_url 的列表。终态发布前固定为空 |
| `GET /tasks/{id}/artifacts/{name}` | 200，Content-Type、Content-Length 与入库文件一致，响应为原始字节。通过任务 ID 和完整产物名精确查库 |

失败任务的快照示例：

```json
{
  "id": "bd28a470-f4f7-4717-9c47-4dabefd9771a",
  "project_id": "broken", "type": "test", "timeout_seconds": 30,
  "status": "failed", "stop_reason": null,
  "created_at": "2026-01-01T10:00:00Z",
  "started_at": "2026-01-01T10:00:01Z",
  "finished_at": "2026-01-01T10:00:02Z",
  "exit_code": 1,
  "error": {"code": "nonzero_exit", "message": "项目测试退出，退出码为 1"}
}
```

running 快照另含可空的 recovery_reason，清理等待中取 cleanup_pending，依赖不可达取 runtime_unavailable。该字段用于解释收尾进度，终态错误由 error 表示。

无效 JSON 返回 400，非 JSON 请求返回 415，超过 8 KiB 的创建请求返回 413，字段错误返回 422。未知任务或未知产物返回 404。排队已满返回 429。服务恢复中、存储空间不足或执行环境暂不可用时，拒绝新任务并返回 503；可用的历史结果继续可读。HTTP 错误体固定为 `{"error":{"code":"…","message":"…"}}`，消息不包含宿主路径、环境变量和堆栈。任务自身失败通过快照表示，查询仍返回 200。

## 4. 状态、数据与并发

SQLite 放在本地磁盘，启用外键、WAL 和同步提交。一个进程级文件锁保护数据目录。所有状态写入走短事务；容器调用、日志读取和进程等待均在事务外。Docker 的阻塞调用在有界线程池内执行，保留独立容量处理取消和回收，以免两个慢任务阻塞控制请求。

| 持久化对象 | 必需字段或约束 |
| --- | --- |
| settings | 数据目录的随机 owner ID、首次绑定的 daemon ID、schema 版本。daemon 身份变化时要求显式处理，防止把另一环境“查不到容器”误判为清理成功 |
| tasks | 单调递增 seq 主键、唯一 UUID、project_id、type、image_id、timeout_seconds、status、三个 API 时间及 deadline_at；内部字段保存 container_id、首个结束原因、恢复原因、暂存结果、最终退出码和错误。暂存结果同时充当收尾进度标记。索引 (status, seq) |
| task_logs | 任务 ID 唯一，保存已收集的原始前缀和 truncated 标志；外键级联删除 |
| artifacts | 主键 (task_id, name)，保存 media_type、字节数、内容 BLOB；外键级联删除。只有关联任务为终态才开放下载 |

**领取与容量。** 两个 worker 按 seq 领取；默认最多另有 32 个等待项。创建在同一写事务内计数并插入。领取通过有状态前置条件的更新完成，只有仍为 queued 的任务能被 worker 接手。取消与领取谁先提交谁生效。终态时间、退出信息与状态一次写入，终态不再改写。

| 当前状态与事件 | 决策与可见结果 |
| --- | --- |
| queued + cancel | 直接变 cancelled；started_at、exit_code 为空，finished_at 有值，没有容器或产物 |
| running + 自然结束 | worker 登记观测到的命令结果。返回 0 且必需产物合法则 succeeded；非零、OOM、启动或收集失败则 failed |
| running + cancel / 超时 / 优雅停机 | 第一次成功登记的原因生效，分别对应 cancelled / timeout / cancelled。worker 停止容器、收尾、发布结果；期间状态维持 running |
| running + 后续结束事件 | 条件更新只接受第一个原因；对已登记的结果继续收尾。收集必需产物失败可将候选成功降为 failed |
| 任一终态 + 取消或迟到通知 | 返回已提交快照；不得修改原终态、结束时间和产物 |

**如何裁决竞态。** 取消、截止计时器和完成观察者通过同一持久化条件更新登记原因。取消事务先检查是否已到截止点，到期则登记 timeout。容器可能物理上已退出但完成事件尚未提交，这时先被服务接受的取消可以获胜；这条语义能通过 HTTP 观察和复现。业务错误码区分 `nonzero_exit`、`out_of_memory`、`start_failed`、`artifact_invalid`、`service_interrupted` 和 `runner_error`。运行中 stop_reason 对调用方显示已接受的取消、超时或停机原因；退出码来自已取得的命令结果，外部强制停止且缺失命令结果时为 null。容器内确认超时也走同一登记路径。判读退出证据时先看已登记原因，再看引擎的 OOM 标志，然后读取入口程序原子发布的命令结果；其余异常退出归为 runner_error。不会只凭容器退出码 137 判断 OOM。

## 5. 执行隔离、期限与数据上限

**执行权限。** 每个容器设置私有 PID 命名空间、普通 UID、drop ALL capabilities、no-new-privileges、默认 seccomp、network=none、restart=no。每任务默认 1 CPU、256 MiB 内存、总内存加交换空间上限同为 256 MiB、最多 64 个进程。Docker socket、宿主目录、宿主环境变量及凭据均不传入任务。镜像内源码归维护者管理；调用方不能指定镜像、入口、任务环境或挂载。API 进程能控制 Docker，应仅向可信本地调用者开放。写层磁盘占用受宿主和存储驱动影响，产物大小上限只约束发布数据；支持任意外部代码前须另行验证每任务磁盘硬配额等隔离能力。

**执行期限。** 从领取开始计时，包含容器创建与启动。服务用单调时钟监控活任务，将 UTC 截止时刻持久化并传给容器入口。入口启动时换算剩余时间，此后用自己的单调时钟计时；过期时跳过命令。容器使用宿主同步的系统时间。入口是容器 PID 1，自己处理命令执行、日志与截止计时，主命令结束或超时后写小型结果记录并退出，命名空间内其余进程随之终止。外部取消直接停止整个一次性容器。即使 API 消失，容器自身的截止计时仍有效；已停止容器的磁盘数据留待恢复程序收集或删除。daemon 或内核不可响应期间，API 只能报告恢复中，不能宣称已完成清理。

**日志。** 入口合并两路输出，用非阻塞、固定块读取，同时检查子进程状态与截止点。保留前 65,536 字节，额外存一个溢出标记字节；对外最多解码前 65,536 字节，恰好达到上限时 truncated 仍为 false。超过上限继续消耗管道数据。主进程退出时排空管道里当时可读的数据，只给收尾有限宽限，避免后台后代持有管道拖住退出。入口将日志实时写到固定文件，容器日志驱动设为 none，避免 daemon 再复制一份无限输出。worker 定期读取有界快照（目标间隔 250 ms），只在前缀增长或标记变化时更新数据库。轮询接口直接读库；容器退出后再取最后一份。UTF-8 截断或无效字节以替换字符显示，上限以原始字节计算。

**产物。** 所有已领取并能完成收尾的任务都有服务生成的 result.json，记录任务、结果、退出信息和收集错误；排队取消没有报告。成功 build 额外要求 app.pyz 不超过 5 MiB。只从已停止容器读取固定路径，只接受一个名称匹配的普通文件，拒绝链接、目录、额外成员和超过限额的流。Docker 文件接口返回 tar 数据，读取时逐项验证并限制总传输量，不将归档展开到宿主文件系统。最终 404 的下载路径始终不能触发文件访问。[Docker 文件复制语义](https://docs.docker.com/reference/cli/docker/container/cp/)

## 6. 强杀、重启与清理

每个容器带 owner 和 task 两个标签。单实例启动时先持有数据目录锁，核对 daemon 身份，按 owner 枚举并交叉核对数据库。对所属容器以不可变 container ID 操作，命名冲突或标签不匹配时停止处理并报告错误。SQLite 与 Docker 之间没有跨系统事务，所以下表按中断位置定义处理结果。

| 服务中断的位置 | 重启后怎么处理 |
| --- | --- |
| 已入队、尚未领取 | 保留原 ID 和队列顺序，使用入队时记录的镜像。镜像已被删除则领取后以 start_failed 结束 |
| 已领取，尚未创建容器 | 按预期名称和标签核查；找到则回收，找不到则按中断收尾。不自动重新执行已领取任务 |
| 已创建，尚未登记 ID 或启动响应丢失 | 按标签找到 created、running 或 exited 容器，接管并清理。不会按名称向它补发 start |
| 正在执行，尚未暂存结果 | 优先保留数据库已登记的取消、超时或停机原因。否则，若容器已退出且结果记录完整，则收集实际结果；仍在运行或证据缺失则登记 service_interrupted、停止容器。保留可读日志 |
| 日志、结果和产物已暂存，容器还在 | 使用同一份暂存结果继续删除容器。确认删除后发布终态，不重新构建产物 |
| 容器已删除，发布事务尚未提交 | 暂存结果足以发布；若查询明确返回“该容器不存在”，删除视为完成。连接超时、权限错误或 daemon 不可用均不能代替这个确认 |
| 终态已提交 | 原状态、日志和产物继续可查；重新启动和重复取消不会重写历史 |

先暂存、再删除、最后公开。这样既能验证终态意味着资源已释放，也避免容器恰好在结果写盘前被删。若删除失败，保留 running 和暂存结果，保留执行槽，以有上限的退避间隔重试，对外显示恢复中的原因。daemon 恢复后先对账再开放领取。容器 create 的响应丢失时按固定身份对账；start 仅针对已登记的完整容器 ID 发起一次。定期扫描 owner 标签，以回收延迟创建的空容器。同一数据目录和任务的延迟 create 只可能得到未启动容器，因为 start 依赖独立的、已登记 ID 的调用。恢复扫描对已领取任务始终先核对身份；遗留容器满足 owner、任务记录和预期名称才删除。标签不一致或无对应记录时报告诊断，交由维护者核查。

正常停机时停止接单和领取，记录正在执行任务的停机原因，回收后再释放锁。进程强杀后独占锁由操作系统释放。保留策略默认保存终态任务 7 天，从 finished_at 起算；启动及定期维护时分批删除已过期的终态任务，日志与产物同事务级联删除，过期 ID 查询为 404。活动任务和待清理记录不能过期。数据卷可用空间低于 128 MiB 时拒绝新任务、优先处理在途任务；SQLite 提交失败时不得确认入队或发布终态。磁盘完全耗尽需要恢复可用空间，服务复原后重新对账。

## 7. 从外部验证

计划入口为 `python -m pytest -q tests/e2e`。E2E 启动真实 HTTP 服务，使用独立临时数据库和真实 Docker daemon。夹具通过正常任务接口提交受控项目；需要检验系统资源时，只读检查该次运行 owner 下的容器。就绪日志、HTTP 状态和实际容器事件用作同步信号。各等待有截止时间，失败时输出最后的状态、日志和容器信息。夹具自身的清理放在断言之后，避免测试替服务完成回收。

| 验收场景 | 可观察的通过条件 |
| --- | --- |
| 成功、失败与构建 | 三类任务执行实际命令。失败测试保留断言和退出码；构建归档可下载并运行。进入终态时容器已消失，下载仍有效 |
| 并发、隔离与背压 | 两个慢任务同时发出就绪标记，各自写相同文件并读回自己的内容。第三个保持 queued。填满等待队列后再提交得到 429，释放槽后队首任务先执行 |
| 两种取消与重复调用 | 等待项取消后没有容器和开始时间；运行项取消后即使子进程另起会话，整个容器仍消失。并发取消、结束后取消均保留同一终态与时间 |
| 超时与竞态 | 测试命令持续输出并派生后代。超时后释放槽；分别在就绪后、终态后发起取消。对同时完成与取消的重复试验，只允许一个已发布结果，报告、状态、产物相符 |
| 有界日志 | 运行中可读到两个输出流的标记。分别写恰好上限和超出一个字节的 ASCII 数据验证 truncated；高吞吐、多字节截断、无换行与后代持有管道均能收尾 |
| 隔离与产物校验 | 在任务内验证非 root、进程上限、无宿主挂载和网络配置；模拟 OOM、缺文件、超大归档与链接型产物。不得发布无效文件，其他任务继续运行 |
| 协议与非法输入 | 验证 400/404/413/415/422/429 及统一错误结构。使用其他任务 ID 查询某产物应得到该任务自己的内容或 404 |
| 强杀、重启与锁 | 对队列、运行中和已完成的混合负载强杀 API。先保持服务离线，独立确认慢任务容器到期停止；再启动，核对排队恢复、旧容器已删除、原历史可查。第二个指向同一数据目录的实例须拒绝启动 |
| 暂存和删除之间的中断 | 使用测试专用进程屏障，分别在暂存提交后、删除确认后暂停 API 并强杀。按原目录重启，两种情况下产物一致、工作容器数均归零 |
| daemon 故障与存储保留 | 在独立测试 daemon 或测试代理上切断执行器连接。清理未确认时保持待恢复，恢复连接后发布一次。用单独数据目录和短保留配置验证过期结果被删除、运行项仍保留 |

实现验收时，README 需在干净环境给出镜像构建、启动、运行 E2E 和重放演示的命令，并注明 Docker 不可用时的诊断。演示脚本走公开 HTTP 接口：启动 → 成功任务 → 失败任务 → 读取慢任务实时日志并取消 → 下载和运行归档。最后在 AI_USAGE.md 对照一次实际修改、对应测试与真实结果，区分 AI 建议和人工判断。

## 8. 已知边界与后续优先级

这是单用户、单机、可信预置项目执行服务。容器共享 Linux 内核，Docker 管理权限属于控制面信任边界。SQLite 数据和执行引擎均位于同一台开发机；主机磁盘毁损不在恢复保证内。提交响应丢失后也没有跨请求去重保证。

若扩展到接收用户上传项目，最先补的是**每任务磁盘硬配额和宿主级故障验收**。选择并实际验证目标存储驱动的配额能力，使用持续写盘、多文件和 OOM 负载检查其他任务、宿主及恢复流程，再决定是否开放新代码来源。若继续只服务本地预置项目，优先保持上述契约可复现。
