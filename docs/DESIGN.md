# 代码任务执行服务设计

调用方向本机服务提交一个预置项目和任务类型。服务返回任务 ID，在独立工作目录中启动宿主机进程，执行期间允许查询、看日志和取消；任务结束后可以下载测试结果或构建归档。本文是实现约定，文末单独列出已在 macOS 验证的进程行为和仍待运行的整体验收。

## 1. 运行环境与信任边界

开发环境为 macOS，部署目标为普通 Linux 服务器，两者使用相同的 Python 服务和 POSIX 进程模型。运行依赖为 Python 3.11+、FastAPI、Uvicorn 和系统提供的 SQLite，普通用户可以启动。服务默认绑定 127.0.0.1；服务器演示可通过 SSH 端口转发访问。每次执行的代码来自维护者随仓库发布的预置项目。请求只能选择项目 ID、任务类型和超时。

题目要求隔离工作目录、控制进程和日志、清理任务资源。宿主机的目录、进程组、管道和文件锁分别承担这些职责。目录权限 0700 防止其他本地用户读写；同一服务账号下的任务仍拥有该账号的系统权限，能访问其可读文件和网络。受支持的项目须在任务进程组内运行，不能自行创建新会话、切换进程组或向控制面发送信号。开放外部用户上传代码会改变这个信任前提。

## 2. 从提交到下载

以请求 `{"project_id":"hello","type":"build"}` 为例：

1. API 校验后在 SQLite 写入 queued 记录，事务提交后返回 HTTP 202。调用方持 ID 即可查询。
2. 调度器在一个短事务中检查空闲槽、按入队序号领取任务、写入 running 与开始时间。默认最多两个运行项、32 个等待项。每个已领取任务启动一个独立的 **runner 进程**，负责这个任务直至收尾。任务之间没有共享工作目录。
3. runner 把 hello 复制到 `work/<id>/src/`，在这里以固定参数启动系统进程。构建写到同一任务的 `out/app.pyz`；示例项目及其他任务的副本保持原样。
4. runner 合并并持续读取 stdout 和 stderr，按块保存有界日志。命令结束、超时或取消时先处理整个进程组，再收集产物。在 SQLite 暂存最终结果和产物后删除工作目录，最后发布终态。
5. 评审下载 SQLite 保存的归档，在工作目录已消失后仍可运行 `python app.pyz` 验证真实输出。

**为什么单独启动 runner。** 取消和超时需要有人持有真实子进程，并负责发信号和 wait。如果把这项责任交给处理 HTTP 的进程，它被强杀时会连带丢失进程句柄。这里每个执行槽最多多用一个轻量 Python 进程。API 重启期间，runner 仍按原期限执行和收尾；新 API 可以从同一数据库读日志、接收取消。每个任务只有一个 runner，没有常驻的外部队列服务。

| 类型 | 在 src 下运行的命令，解释器取服务的绝对路径 | 成功依据 |
| --- | --- | --- |
| lint | `python -m compileall -q .` | 语法检查退出码为 0，README 说明检查范围 |
| test | `python -u -m unittest discover -s tests -v` | 项目自带用例通过；故意失败的预置项目应留下断言及非零退出码 |
| build | `python -m zipapp . -o <任务输出目录>/app.pyz` | 命令成功且归档收集成功；E2E 实际下载并运行归档 |

## 3. HTTP 契约

普通响应使用 JSON。输入的项目和类型必须命中固定表。timeout_seconds 可省略，默认为 30，接受 1–300 的整数；拒绝布尔值、额外字段、任意命令、路径和 URL。

| 接口 | 响应与边界行为 |
| --- | --- |
| `POST /tasks` | 202，返回 `{"id":"<uuid>","status":"queued"}`，Location 指向状态接口。每次成功提交创建独立任务，网络重试可能产生第二个 ID |
| `GET /tasks/{id}` | 200，返回 id、project_id、type、timeout_seconds、status、created_at、started_at、finished_at、stop_reason、exit_code、error。时间为 UTC RFC 3339；尚未发生或未取得的值为 null |
| `GET /tasks/{id}/logs` | 200，返回 `{"text":"…","truncated":false}`。从空串开始，可在运行中反复读取已有前缀 |
| `POST /tasks/{id}/cancel` | queued 时直接结束，返回 200；running 时登记停止请求，返回 202 和当前快照。重复调用返回当前快照，终态时为 200，保留原结束时间 |
| `GET /tasks/{id}/artifacts` | 200，返回 `{"items":[]}` 或每项含 name、size_bytes、download_url 的列表。结果发布前为空 |
| `GET /tasks/{id}/artifacts/{name}` | 200，以记录的媒体类型返回完整字节。按任务 ID 和产物名精确查库；未知产物为 404 |

请求错误体统一为 `{"error":{"code":"…","message":"…"}}`。无效 JSON 为 400，超出 8 KiB 为 413，非 JSON 创建请求为 415，非法字段为 422，未知任务为 404，队列满为 429，存储暂不可用为 503。测试断言失败发生在任务中，查询本身仍返回 200。典型结果如下：

```json
{
  "id": "bd28a470-f4f7-4717-9c47-4dabefd9771a",
  "project_id": "broken", "type": "test", "timeout_seconds": 30,
  "status": "failed", "stop_reason": null, "exit_code": 1,
  "created_at": "2026-01-01T10:00:00Z",
  "started_at": "2026-01-01T10:00:01Z",
  "finished_at": "2026-01-01T10:00:02Z",
  "error": {"code":"nonzero_exit","message":"项目测试退出，退出码为 1"}
}
```

## 4. 状态、并发与数据所有权

数据放在本机磁盘。SQLite 开启 WAL、外键、同步提交和有界 busy timeout。API 与 runner 使用各自的连接，数据库事务中只做读写；复制目录、排空管道、等待进程和删目录均在事务外完成。

| 对象 | 内容和约束 |
| --- | --- |
| tasks | seq 递增主键、唯一 UUID、项目及类型、超时、状态、三个时间、执行期限、已登记的结束原因、退出码、错误。内部保存启动意图和暂存结果。索引 (status, seq) |
| task_logs | 每任务一条有界原始字节前缀和截断标志，外键关联任务 |
| artifacts | 主键 (task_id, name)，保存 MIME、字节数和内容，仅终态可读 |
| 本地文件 | 数据目录的 API 独占锁、每个任务的 runner 锁，以及私有的 work/<id>/{src,out,tmp}。锁文件在 work 之外，生命周期覆盖工作目录删除 |

**状态流转。** queued 可以转为 running 或 cancelled。running 可以转为 succeeded、failed、timeout 或 cancelled。领取时写 started_at，包含准备目录的时间；终态发布时写 finished_at，包含清理时间。队列取消没有 started_at 和 exit_code。自然非零退出为 failed，进程受信号终止时保留实际负信号编号。命令从未启动或结果未知时 exit_code 为 null。

**并发与取消。** 调度按库中 running 数量分配槽，包含 API 重启前仍在执行的任务、正在回收和正在发布结果的任务。入队检查与插入、领取与状态修改各自原子完成。取消、超时和完成观察通过同一条件更新登记首个结束原因。到期以后才收到的取消优先登记超时；已经登记自然完成的任务继续发布结果。物理进程可能在 API 观察退出前已结束，此时先登记的取消可以生效。终态只写一次。runner 独立监控从领取起算的单调时钟期限，并以短间隔检查持久化取消原因；复制结束和启动命令前也各检查一次。

**发布。** 退出码 0 且必需产物有效才可 succeeded。语法或断言失败、启动失败和产物非法分别返回 nonzero_exit、start_failed 和 artifact_invalid。正常收尾的已领取任务均生成 result.json，包含任务 ID、终态、退出码和错误；排队取消没有报告。先将结果和文件放进一次 SQLite 事务，删除工作目录后再原子发布终态；期间所有产物对外不可见。删除失败保留暂存结果、执行槽和可诊断的清理原因，退避重试。下载接口只从已发布的数据库记录取字节。

## 5. 宿主机上怎样执行与回收

**目录和参数。** 数据根目录由维护者配置，每个任务 ID 由服务生成。复制预置目录时只接受普通文件和目录，拒绝符号链接和特殊文件。使用绝对解释器、参数数组、指定 cwd、空 stdin 和最小环境；临时文件与 HOME 指向任务私有目录。服务账号及其子进程均以普通用户运行。子进程关闭无关文件描述符，尤其不能继承 API 实例锁、数据库连接或 runner 锁。构建只收集固定输出名，通过可信目录描述符打开，用 O_NOFOLLOW 和 fstat 验证普通文件，边读边限制为 5 MiB。

**启动与信号。** runner 自己在独立会话中启动并脱离 API 的标准流。它用 `Popen(argv, start_new_session=True, ...)` 启动任务命令，命令 PID 同时是进程组 ID。取消、超时及主命令自然退出都走同一收尾路径：向该组发 SIGTERM，短暂宽限后以 SIGKILL 结束剩余成员，最后 wait 回收直属子进程。自然退出也执行这一步，因为主命令可能留下持有日志管道的后台进程。runner 自身在组外，能够继续写结果和清理目录。

**为何先发组信号再 wait。** 先 wait 会释放组长 PID，后续在极端情况下可能命中被复用的编号。runner 先观察直属命令退出，保留其待回收身份，再完成组信号操作。macOS 可用 kqueue 的 NOTE_EXIT，Linux 可用 waitid 配合 WNOWAIT；两条路径分别做平台验收。正常路径从持有的直属子进程取得退出码；重启后的 API 不拿数据库里的旧 PID 发信号。

**有界 I/O。** stdout 和 stderr 合并进非阻塞管道。runner 每次只读固定大小的数据块，保留前 65,536 个原始字节，恰好达到上限时 truncated=false，读到额外一个字节才置 true。超额部分继续排空。最多每 250 ms 批量提交新前缀，退出时再刷新。高频输出期间也检查截止时间和取消，防止日志写入饿死控制操作。UTF-8 解码用替换字符处理截断。进程退出观察独立于管道 EOF，收尾排空有界，后代持有写端不会无限阻塞。

## 6. 重启与异常边界

启动 API 前取得数据目录独占锁，第二个 API 实例收到明确错误。调度器在把任务改为 running 前持有对应任务的独占 flock，通过 pass_fds 把同一个锁描述符交给 runner；父进程在交接后关闭自己的描述符，任务命令不继承。恢复方尝试非阻塞加锁，区分“原 runner 仍负责”与“无人负责”。新的 API 只在核对库中已有工作后开始领取。

| 中断点 | 可恢复行为 |
| --- | --- |
| 已入队、未领取 | 保留 ID 和次序，按 FIFO 继续执行 |
| 已领取、还没启动 runner | 任务锁已释放且无命令启动意图，标记 failed / service_interrupted，清理准备目录，不重跑已领取任务 |
| API 被强杀，runner 仍在工作 | 锁被占用，原 runner 继续读取消、执行超时、清理和发布结果；新 API 只接管查询和调度。即使 API 一直离线，runner 的时限仍生效 |
| 结果已暂存、目录尚未删除 | 先看锁。runner 仍在时让其收尾；锁已释放时恢复程序验证任务私有路径，补做幂等删除并发布原结果 |
| 目录已删、终态尚未发布 | 使用已暂存结果发布。目录已不存在视为删除成功，不重写日志或重新构建 |
| 已发布终态 | 同一 ID 返回原状态、退出信息、日志和产物 |

**同时丢失执行器的边界。** API 退出与 runner 本身遭受 SIGKILL 是两种故障。runner 启动任务前持久化“可能存在活进程”，在确认组回收后清除该标记。如果 runner 锁已释放、标记仍在且没有暂存结果，恢复方无法单靠旧 PID 证明任务组身份。记录 `cleanup_unverified` 并隔离该工作目录，保留其槽、向查询者返回 running 和 recovery_reason，等待维护者核实资源后以 failed / runner_lost 收尾。此类故障下不承诺自动清除失去监管的后代；正常 API 重启能够自动恢复。主机已确认重启时旧用户进程已结束，可据此完成目录清理。只在确认资源状态后发布终态。

正常关闭 API 时停止接单与领取，向 running 项登记 service_shutdown，让 runner 回收并等待它们收尾；queued 留待重启。服务存储位于本机磁盘，终态历史默认保留七天，按 finished_at 分批过期，事务内级联删除日志和产物，随后各查询返回 404。活动记录和待清理目录不参与过期。存储写入失败时不确认入队或发布成功，已有任务仍尝试停止子进程。宿主硬盘损坏、同账号恶意代码和主动脱离任务组的程序超出恢复承诺。

## 7. 验收和演示

服务 E2E 计划使用 `python -m pytest -q tests/e2e`。在 macOS 和 Linux 使用相同 HTTP 测试；每次创建独立数据目录、实际启动服务、提交示例并检查宿主进程和工作目录。用进程就绪标记和有截止时间的轮询同步。涉及回收的断言先检查资源，再由测试夹具兜底清理。示例中的 unittest 是被执行的任务负载。

| 场景 | 可观察的通过条件 |
| --- | --- |
| 三类任务与失败用例 | 语法检查、测试和构建通过；故意失败项目产生真实断言及退出码；目录消失后下载 app.pyz 并运行，输出与示例一致 |
| 并发与隔离 | 两个慢任务同时就绪并各自写同名文件，互不覆盖；第三个排队。填满队列得到 429，空出槽后按入队顺序开始 |
| 排队及运行中取消 | 排队取消没有开始时间和目录；运行取消回收组内忽略 TERM 的后代。多次取消保留结束时间与产物 |
| 超时与自然结束 | 超时任务停止，后续任务取得槽。主命令提前正常退出并留下持有管道的后代时，退出码仍为 0，后代消失，日志可读 |
| 日志边界 | 检查 stdout、stderr、无换行、高吞吐、恰好上限和多一字节；截断标记准确，服务仍能及时取消或超时 |
| 协议与文件 | 非法字段、未知 ID、过大请求、未知类型返回约定错误。链接型或超大产物构建失败，源码副本不能覆盖预置源 |
| API 重启与持续监管 | 强杀 API 并保持其离线，确认 runner 按期回收。另在任务仍活跃时重启 API，用原 ID 取消并验证总并发不超限。验证历史产物和 queued 任务仍可用 |
| 收尾中断与失去监管 | 在暂存后或删目录后中断 runner，重启后只发布一份结果。单独中断仍持有活任务的 runner，验证进入待核实状态，不向旧 PID 发信号 |
| 结果一致性 | 在自然结束、取消与超时交错时重复查询，检查终态、报告与退出码一致。启动第二个实例被拒绝，缩短保留期只删除终态历史 |

**本次机制验证。** 在 Darwin arm64 上以真实进程分别演练主动取消、上层进程被 SIGKILL 后 runner 自行超时、主命令正常退出并留下忽略 TERM 的后代。三例最终均观察到该后代 PID 消失，主命令实际退出码分别为 -15、-15、0。实验确认 macOS 上的会话、进程组信号和延迟 wait 路径；HTTP、持久化、锁交接以及 Linux 路径仍需以上 E2E 验收。

演示按评审可直接复现的顺序：启动服务、提交成功和失败任务、在慢任务运行中看到日志并取消、查看进程与目录回收、下载产物并执行。README 给出干净环境安装、启动、测试和重放命令；AI_USAGE.md 引用实际运行结果与人工修改记录。

## 8. 后续优先级

若上线场景仍是可信内部仓库，优先在目标 Linux 发行版持续运行崩溃恢复和进程回收 E2E，并验证 runner 单独死亡时的处置流程。若产品开始接收陌生仓库或上传包，先设计独立执行身份、文件与网络访问控制、进程和磁盘配额，再开放新代码来源。两者的安全责任不同。
