# AI 使用与验证记录

本项目使用 Codex 完成需求分析、方案比较、代码编写、测试、命令执行和文档整理。候选人要求在自己的 Mac 上完成开发与演示，以 E2E 验收，并讨论了标准库 HTTP 与 FastAPI 的取舍。代码、测试执行与下文的故障定位由 Codex 完成。候选人可在面试前自行重放这些实验，补充亲自审查的部分。

## 哪些建议改变了实现

最初的方案曾考虑容器运行环境。候选人明确指定宿主机执行，最终实现采用 macOS 的独立工作目录、会话、进程组和 kqueue。HTTP 层最初选择系统 Python 3.9 的标准库。核对机器上已有 Python 3.12 和 uv 后，改用 FastAPI 和 Pydantic，以便评审直接使用 /docs 调用接口。

执行器保留独立进程。这个决定可以通过强杀 API 来检查：在 API 离线期间，原 runner 仍能执行超时、回收同组后代并清理目录。另有测试在任务仍活跃时重启 API，通过原 ID 取消任务。

## 一次真实的失败与修正

首次运行演示，hello 项目的测试日志已经显示 OK，任务却返回 failed，退出码为空。定位到 runner 收尾阶段的 killpg 调用。用一个快速退出的真实子进程复验时，macOS 的 ps 显示组长状态为 Z；向该组探测或发送 TERM、KILL 均得到 EPERM，随后 wait 读到的真实退出码为 0。

修正后，runner 在发出最后一次组信号前保留直属子进程的待回收身份。遇到 EPERM 时读取组成员状态，如果还有活进程则保留错误；确认组内只剩僵尸或已无成员时继续 wait。成功测试、故意失败的断言、带后代的取消及后台后代持有输出管道的情况分别验证。这样既保留主命令的真实结果，也能发现遗漏清理的后代。

## 可重放的验证

在项目根目录运行：

```bash
uv sync --locked --python 3.12
uv run --locked python -m unittest discover -s tests/e2e -v
uv run --locked python scripts/demo.py
```

本机 E2E 覆盖输入与状态码、六种状态、两个并发槽、排队容量、重复及竞态取消、超时、日志限量、真实下载、单实例锁、优雅停机、强杀重启及分阶段结果发布。测试从操作系统检查已知后代 PID 消失，下载归档后实际运行，得到 Hello, Mac!。演示中的 broken 项目保留真实失败断言，用于核对 stderr 与退出码。

## 仍有边界

本机测试使用可信的预置项目。没有做整机断电或物理磁盘故障实验，也未验证同账号恶意代码的隔离能力。runner 恰好在命令创建后、PID 写入前消失的窄窗口，依靠保守的恢复策略处理，尚未对这一指令级时序做确定性故障注入。
